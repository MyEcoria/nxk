# AGENTS.md — nxk

This file guides AI coding agents working on **nxk**. Follow it on every task
(dev, debug, docs, benchmarks).

## 1. What nxk is

- Microkernel in **pure Rust**, no host OS, for NVIDIA Tegra X1 (Nintendo
  Switch Erista / Mariko: 4x Cortex-A57), run as a **video game
  console**: library UI, GPU 3D engine, games on an SDK (`jeux/`).
- EL1 keeps only: address spaces, threads, scheduler, IPC, capabilities,
  IRQ routing, futex. Everything else (drivers, fs, net, services) runs as
  ordinary **EL0** programs with only the capabilities granted to them.
- User programs are **ordinary Rust with `std`** on target
  `aarch64-unknown-nxk` (see `std/` + `tools/mkstd.py`). `user/libnx` is the
  `no_std` system library underneath `std`.
- Validation today is in the `tegra_qemu` emulator (sibling
  directory, QEMU fork). **Objective is real physical Switch hardware
  (Erista / Mariko): implement for the physical Switch, not only for
  the simulator.** New code must be hardware-compatible (datasheets,
  `refs/`, real Tegra X1 behavior); use the emulator only as fallback
  validation, never as an excuse for emulator-only shortcuts.
- Hardware status: nxk runs on a physical **Erista** Switch through
  hekate's L4T entry and `hwboot/nxk-bl31` (EL2; PSCI `CPU_ON` for
  cores 1-3), on its 4 cores and with its SD card, up to the shell over
  `usbcon`, the USB-C serial console (`tools/usbterm.py` on the PC;
  UART-A pads are internal). `ktest` 29/29 and `stdtest` 17/17 pass
  there. Run log and expected screen output: `hwboot/README.md`.
- Syscall convention: `svc #0`, number in `x8`, args in `x0`–`x5`, result in
  `x0`, errors as `-errno` (Linux values). Single source of truth: `abi/`
  (`nxk-abi` crate shared by kernel, libnx, std).
- Code, comments, logs and docs are in English. Keep them in English;
  translate any French leftovers you touch.

## 2. Layout

```text
abi/        nxk-abi: syscall numbers, errors, rights, service protocols
kernel/     the EL1 microkernel (crate `nxk`)
shader/     nxk-shader: shader IR, validator, CPU reference, SASS compiler
            (`cd shader && cargo test` on the PC; used by `user/gpu`, `jeux/nxgfx`)
user/       workspace: libnx (no_std) + init, shell, drivers, services, tests
std/        Rust std port: std/library overlay, target JSON, linker script
apps/       ordinary std programs: hello-std, stdtest
jeux/       games (std) and nxgfx, the game SDK (on nxk-abi alone)
services/   game catalogs ("services" on screen, std) and nxsvc, their SDK
            (`abi::proto::provider`; installed as /services/NAME/NAME):
            demo, luna (Amazon Luna), lunacore (its logic: `cargo test
            --manifest-path services/lunacore/Cargo.toml` on the PC), nxhttp,
            nxdtls (DTLS 1.2, tested against `openssl s_server` on the PC),
            nxopus (Opus/CELT decoder ported from libopus; `cargo test` on
            the PC against libopus's vectors)
bench/      nxk vs L4T comparison (lbench, scripts, RESULTS.md)
tools/      build.sh, mksd.py, run.sh, debug.sh, nxtest.py, mkstd.py,
            usbterm.py, tegra_qemu patches, ...
hwboot/     physical Switch bring-up: RCM injector, hekate entry, nxk-bl31
            EL3 monitor, SD setup (mksd-hw.sh), test-bl31.sh
refs/       hekate / Atmosphere — hardware documentation only, never compiled
build/      generated artifacts (nxk.elf symlink, bootfs.img) — git-ignored
docs/logo/  pixel-art logo SVGs, generated by tools/mklogo.py
```

Kernel internals: `kernel/src/{arch,drivers,kern,mm,sync,boot.rs,...}`.
User services: `user/{console,clk,i2c,power,fan,cpufreq,gpu,sd,fs,display,input,usb,usbcon,net,wlan,bluetooth,init,shell,...}`.
Tests: `user/ktest` (kernel tests, ~27), `apps/stdtest` (std tests, ~18).

`tegra_qemu/` (sibling of `nxk/`, not covered by this file) is an external
dependency. Prefer fixing nxk side; touch the emulator only when the bug is
clearly in device emulation, and say so explicitly. Emulator changes nxk
relies on are kept as patches in `tools/` (`tegra_qemu-usb-otg.patch`: OTG
device mode behind chardev `usbotg`, needed by `nxtest.py --usb-cmd`;
`tegra_qemu-touch-irq.patch`, applied after it: the touch panel's
interrupt on GPIO X1, needed by `nxtest.py --tap`;
`tegra_qemu-gpu.patch`: GM20B's unit counts and FE power mode in the
GPU model, needed for `gpu on` to reach its channel;
`tegra_qemu-mc-tz.patch`: the TX1 offsets of `MC_SECURITY_CFG0/1`, needed
for PSCI calls after boot under `nxk-bl31`).

## 3. Mandatory workflow: build, run, test

Build directories live **outside the repo** in `~/.cache/nxk/`
(`$NXK_CACHE` overrides). Never commit `target/` or `build/` contents.
Prerequisites: stable Rust + `rust-src`, `aarch64-unknown-none` and
`aarch64-unknown-none-softfloat` targets, compiled `tegra_qemu`, `mkfs.fat`,
`pyfatfs`.

```bash
./tools/build.sh                  # user progs -> bootfs -> std chain -> kernel
./tools/mksd.py -o build/sd.img   # FAT32 SD image (/bin/*)
./tools/run.sh                    # build + boot; shell on stdio (Ctrl-A X quits)
./tools/nxtest.py -c ktest -c stdtest --sd build/sd.img
```

Key details agents must respect:

- `tools/build.sh` is the canonical build: user workspace
  (`CARGO_TARGET_DIR=$cache/target-user`), then std chain
  (`tools/mkstd.py`, toolchain named `nxk`), then apps with
  `RUSTC_BOOTSTRAP=1 CARGO_TARGET_DIR=$cache/target-apps`, then
  `mkbootfs.py`, then kernel
  (`CARGO_TARGET_DIR=$cache/target-kernel`). Do not rebuild pieces by hand
  in repo-local `target/` dirs.
- `apps/` requires the `nxk` toolchain (`apps/rust-toolchain.toml`,
  `channel = "nxk"`) prepared by `mkstd.py` (hardlinked stable Rust + ported
  std, `-Z build-std`; see `apps/.cargo/config.toml`). If `std/` changed,
  `mkstd.py` invalidates the apps cache — always go through `build.sh`.
- Kernel target is `aarch64-unknown-none-softfloat`, `target-cpu=cortex-a57`
  (see `kernel/.cargo/config.toml`). Kernel and user profiles use
  `panic = "abort"`, LTO, `codegen-units = 1`.
- QEMU path: `$QEMU`, default `~/.cache/tegra_qemu/build/qemu-system-aarch64`.
  Fail fast if missing.
- `nxtest.py` drives UART-A over a socket, waits for the `nxk>` prompt, types
  `-c` commands, exits 1 on timeout. Useful flags: `--sd`, `--machine
  tegrax1plus` (Mariko), `--monitor ELF --dtb DTB` (EL2 under PSCI monitor),
  `--net [hostfwd...]`, `--usb-kbd --keys`, `--bt` (an emulated BCM4356 and
  Pro Controller on UART-D, `tools/btfake.py`), `--usb-cmd CMD` (typed on the
  USB-C console, the script as the PC), `--usb-put LOCAL:REMOTE`,
  `--dbg COMMANDS` (`tools/nxdbg.py` over the USB-C console),
  `--uart-log FILE` (all UART-A output, also the logs read unshown while
  the USB-C console runs), `--screendump out.ppm`, `--timeout SECS`.
  Extra QEMU args via `NXTEST_QEMU_ARGS`. The shell's `sleep N` is in ms.
- On a connected Switch, iterate on a boot driver without an SD swap:
  `./tools/build.sh && ./tools/usbterm.py --reload DRIVER -c "..."`
  (init's `RESTART`, see `hwboot/README.md`). Kernel, init, shell and
  boot-path changes still need `hwboot/mksd-hw.sh` and a reboot.
- **Strict rule: after any kernel / libnx / service / std / app change, run
  `./tools/build.sh` then `./tools/nxtest.py -c ktest -c stdtest --sd
  build/sd.img` (add relevant `-c` commands, e.g. `-c bench`,
  `-c "run hello"`). Paste failures verbatim; on boot timeout use the
  per-CPU `PC/EL` dump `nxtest.py` prints (via `nm` symbolization) to
  localize hangs.
- Boot-path changes (`kernel/src/boot.rs`, kernel console / framebuffer
  mirror, early MMU, `hwboot/`) also run `./hwboot/test-bl31.sh`: it boots
  the same `bl31.bin` used on hardware, with and without hekate's screen.
- Debugging: `./tools/debug.sh` (like `run.sh` plus `-s -S`, GDB on `:1234`):
  `aarch64-none-elf-gdb build/nxk.elf -ex 'target remote :1234'`. Kernel keeps
  debug symbols (`debug = true` in release profile).
- Benchmarks: see `bench/README.md`. For L4T-comparable numbers build with
  `NXK_FEATURES=idle-poll ./tools/build.sh`. Reproduce with
  `./tools/nxtest.py -c bench`; compare via `bench/compare.py`.

## 4. Architecture rules (do not break)

- No GUI toolkit or windows: the shell stays on the serial and USB-C
  consoles. The screen is the `display` service's: the game library
  (cards from `/games`), then status pages and a read-only mirror of the
  USB-C terminal; a game takes the whole screen (`display::SCANOUT`,
  three block-linear images, flips at the vertical blank) and gets the
  input `display` routes to it. Catalogs other than the built-in Intern
  (`/games`) are card programs `display` runs and talks to
  (`abi::proto::provider`), never code in the kernel or in `display`. Games draw through `gpu`'s command
  streams (`gpu::RENDER`: checked before anything runs), never by
  writing GPU registers or pushbuffers themselves.
- EL1/EL0 split: no driver or filesystem logic in the kernel. Services get
  least-privilege capabilities; designate objects only via handles with
  rights + generation (revocation by generation bump).
- Kernel style: one kernel stack per core (seL4 model, no mid-call blocking),
  big global lock + lock-free fast path for stateless calls (`clock`,
  `getcpu`, `gettid`), tickless 32-priority O(1) scheduler, synchronous IPC
  (6 words in regs + up to 4 KiB UTCB + up to 4 handles), timeouts on all
  blocking calls, per-core run queues with idle-core balancing.
- Memory: buddy allocator, `DC ZVA` zeroing, ASID-tagged ASs, demand paging
  (incl. multi-core races), enforced W^X, ASLR for static-PIE / heap / stacks,
  MMIO/DMA via `shm_*` + `mmio_map`/`mmio_derive`, exclude MC carveouts and
  `/reserved-memory`.
- Security: Spectre-v2 mitigation on process switch (default feature),
  faulty program is killed without taking down the rest.
- `std` support matrix in `README.md` ("What `std` provides") is normative:
  extend it rather than regress it (no unwinding / backtraces: `panic=abort`).
- `abi/` is the single source of truth for syscall numbers and protocols.
  Never duplicate numbers in kernel/user/std.
- Pipes (`endpoint_create` tube mode) are unbuffered rendezvous: writer blocks
  until a reader takes the data (`Command::output` reads both outputs in
  parallel for this reason). `fs` refuses to delete an open file (`EBUSY`).

## 5. Coding conventions

- Rust edition 2021, `cargo fmt` clean, `cargo clippy` warning-free for new
  code. Keep terse English comments (max 2 lines per block, why-only for
  hardware quirks such as GIC Group 0→1 from EL3 or the secondary-core
  wake sequence: SB reset vector → PMC power partition → voltage locks
  → CAR resets); translate any French comment you touch.
- `no_std` in `kernel/` and `user/libnx`; ordinary `std` in `apps/` and most
  of `user/` services where already used. Do not add external crates without
  need; check `Cargo.lock` impact and offline/air-gapped builds.
- New user program: create crate under `apps/` (std) or `user/` (system),
  register in workspace `Cargo.toml` **and** in the `progs`/`apps` lists in
  `tools/build.sh`, plus SD install if needed (`tools/mksd.py`).
- New syscall: add to `abi/`, wire kernel handler + libnx wrapper + std
  mapping if applicable, document in `README.md` syscall table, cover with a
  `ktest` case.
- Keep `README.md`, `hwboot/README.md` (hardware run log),
  `bench/README.md`, `bench/RESULTS.md` accurate when behavior, tables,
  or numbers change.

## 6. Guardrails (flexible, but be explicit)

- `refs/` is documentation only: read, never compile, never commit changes
  there.
- `tegra_qemu/` is a large external tree: read-only by default. If a fix
  belongs there, explain why nxk side cannot fix it and keep the diff minimal.
- Target real Switch hardware: emulator gaps are documented in README
  ("Limits": xHCI firmware, SD power/pins, DSI panel init, GPIO buttons,
  GPU/audio/Wi-Fi data path/Joy-Con/DVFS). Closing these gaps to run on a physical
  Switch is the objective — implementing real-hardware drivers, init
  sequences, and power/clock handling is in scope. Power-unsafe
  clock/voltage code is allowed only with explicit justification and safe
  defaults; never add shipless drivers (every driver must target a real
  Tegra X1 / Switch chip).
- Do not commit `build/`, `*/target/`, `~/.cache/nxk/`, SD images, or
  `screendump` PPMs. Do not invent URLs.
- Verify by execution (build + `nxtest.py`) rather than by reasoning. If a
  change targets physical Switch hardware and cannot be fully tested in
  the emulator, state what was and was not covered and why the code is
  still correct for real hardware (datasheet section, `refs/` reference,
  register sequence).

## 7. Technical choices (mandatory)

- For every technical choice (design, hardware sequence, boot path,
  protocol, data structure, crate, trade-off between approaches), work out
  **several solutions** (at least two): for each, what it involves,
  pros/cons (hardware safety, complexity, performance, maintenance).
  **Do not ask the user to pick: consult the advisor** (the `advisor`
  tool) with the options, take its answer into account, decide, and
  implement. Report the options and the decision afterwards (commit
  message, docs or the final answer), so the user can overrule it.
- Call the advisor for every question you would otherwise put to the
  user, at every major choice, after each measurement that changes the
  picture, when stuck, and at the end of a step to ask for new avenues.
  Not once per task: often. Bring its new ideas to the next step.
- **Always choose what is best for the result** (frames per second,
  latency, memory, quality, robustness), even when it costs much more to
  write: more code, a harder design, a longer compiler or driver change.
  Never pick the cheaper option for being cheaper; the cheap one is only
  right when it is also the best (or equal) on the result. Measure on the
  console to decide when the answer is not obvious.
- Ask the user only for what cannot be decided from the code, the
  measurements and the advisor: something outside the repository, a risk
  to their hardware or data, a destructive or outward-facing action, or a
  reboot of their console.
- Mechanical changes with a single sensible option (typo, rename,
  following an existing pattern) need no advisor call; say so when skipping.

## 8. Commits (mandatory)

- After every task, `commit` **and** `push` the result (do not leave changes
  unpushed in the working tree).
- Message format (Conventional Commits, all in English):

  ```text
  <type>(<scope>): <short imperative subject, max 72 chars>

  [<body: what changed and why, 1-3 sentences.>]
  [Tested: <commands run, e.g. ./tools/build.sh; ./tools/nxtest.py -c ktest -c stdtest --sd build/sd.img>]
  Co-authored-by: <exact-model-id> <noreply@example.com>
  ```

- Allowed `type`: `feat` (new syscall, service, feature), `fix`, `docs`,
  `refactor`, `test`, `bench`, `tools`, `chore`.
- Allowed `scope`: `kernel`, `abi`, `std`, `apps`, `tools`, `bench`, or
  `user/<service>` (e.g. `user/fs`, `user/net`, `user/shell`, `libnx`).
- One logical change per commit; split unrelated changes.
- Never commit `build/`, `*/target/`, `~/.cache/nxk/`, SD images, or
  `screendump` PPMs.
- Every commit message must include a `Co-authored-by` trailer naming the AI
  model actually used. Replace `<exact-model-id>` with the exact model id
  (e.g. what `opencode models` reports). Never omit it, never invent a human
  author.
